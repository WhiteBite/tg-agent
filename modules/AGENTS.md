# modules/ — реестр функциональных модулей

Пакет несёт контракт подключаемых функциональных модулей. Ядро остаётся тонким:
модуль описывает свои миграции, HTTP-маршруты, MCP-инструменты и исполнитель
фоновых заданий, а `modules/__init__.py` собирает их в один реестр.

Сейчас в реестре один модуль — `downloads` (`modules/downloads.py`).

## Контракт

Модуль — это `dict` со строго проверяемыми полями (валидатор `_validate` в
`modules/__init__.py`):

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `str` | уникальный идентификатор, непустой |
| `version` | `int` | версия схемы модуля |
| `schema` | `fn(conn)` | идемпотентный DDL; вызывается из миграции `db.py` (v7+) |
| `workspace` | `{(method, path): fn}` | маршруты поверх workspace-API |
| `mcp` | `[{name, description, fn, gate?}]` | MCP-инструменты |
| `runner` | `fn(job_id) -> dict` | запуск фонового исполнителя задания |

Правила, которые ловит валидатор:

- ключ маршрута — строго `(method, path)`, `method` из `GET`/`POST`, `path` без
  ведущего и хвостового слэша; GET-функции получают `(db, params)`, POST — `(db, body)`;
- у MCP-спеки `name` начинается на `tg_`, есть непустой `description` и `fn`;
- `gate` — один из `None` (умолчание `downloads`), `"downloads"`, `"forwards"`,
  `"any"`. `confirm=True` в модуль не выносится — проверка живёт в самой функции.

## Точки подключения ядра

Модуль встраивается в ядро в трёх местах, не правя его логику:

1. `db.py` — миграция создаёт таблицы модуля через `modules.ensure_schema(conn)`;
2. `workspace_api.py` — маршруты из `modules.workspace_routes()`;
3. `server.py` — инструменты из `modules.mcp_specs()`, каждый под своим гейтом
   (`_gate_on`).

## Отключение и переиспользование

- `TG_MODULES_OFF="downloads,…"` убирает модуль из реестра целиком: ни маршрутов,
  ни инструментов, ни исполнителя, ни схемы.
- Общая инфраструктура — `jobs.py` (сохраняемые задания `jobs`/`job_items`) и
  `sources.py` (выбор источников + подборки). Следующий модуль берёт их, а не
  копирует.

Новый модуль — скилл `add-module`.
